# Pages or Workers? What moving the kit would change

For the kit's maintainer. An assessment, not a plan: nothing below has been built or tried on a
real Workers project. Vendor pages read 2026-10-11; kit code read at `35e9b42`. The short
version lives in `skills/new-website/references/WEBSITE_ARCHITECTURE.md`, Part 1.

**Owner decision, 2026-10-11: stay on Pages for now.** "When to look again", below, lists
what would reopen it.

## The question

The kit puts every site on Cloudflare Pages. Cloudflare's
[Pages docs](https://developers.cloudflare.com/pages/) now open with: Workers "is
Cloudflare's primary platform for building applications. Start new projects with Workers."
The same page still lists Pages as "Available on all plans", and the Pages docs name no end
date. Cloudflare's [blog](https://blog.cloudflare.com/full-stack-development-on-cloudflare-workers/)
announced in April 2025 that Pages stays supported, while "all of our investment,
optimizations, and feature work" would go to Workers. So: should the kit move, and what
would that touch?

## Recommendation

Stay on Pages for now. No site has to move. If the kit moves later, move it as a redesign
that drops the middleware (route B below), not as a straight port (route A), and try it on
one throwaway site first. The reasons, and the best argument against them, are under
"What is checked and what is judgment".

## How a kit site runs on Pages today

1. **Deploy.** Cloudflare builds on a push (Git integration), or takes an upload
   (`wrangler pages deploy`). Two-stage sites build `production` as the live site and `main`
   as the preview at `main.<project>.pages.dev`.
2. **Files.** Pages serves `dist/`, with `public/_headers` and `public/_redirects`.
3. **Middleware.** `functions/_middleware.ts` sits at the root of `functions/`, so Pages
   runs it in front of every request. It does two jobs, both on `*.pages.dev` hosts only:
   preview hosts get `X-Robots-Tag: noindex`, and the project's own address
   `<project>.pages.dev` redirects to the live domain once `CANONICAL_URL` is set. In
   analytics server mode it has a third, on the live domain: it sends each page view to
   Plausible, and `functions/go/email.ts` counts email taps.
4. **The cost of 3.** Because the middleware runs on every request, every request is a
   Functions request and counts against the free plan's 100,000 a day
   (`CLOUDFLARE_FIRST_DEPLOY.md`, "set Fail open").

The middleware exists because of two gaps. Pages adds noindex to preview deployments; its
docs promise nothing like it for `<project>.pages.dev`. And the Pages docs describe no way
to turn that address off, only a
[redirect](https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/).

## How the same site would run on Workers

A Worker with static assets is a config file (`wrangler.jsonc`) that names `dist/` as the
assets folder. A request that matches a file is served straight from there, free and
without limit, and no code runs. Code runs only when no file matches, unless the config
sets `run_worker_first`.

There are two ways to get there.

### Route A: port the middleware as it is

Compile `functions/` into a Worker script (`wrangler pages functions build`) and set
`run_worker_first: true`, so the script still sees every request.

- Every request stays a billed request. Cloudflare's guide says middleware through
  `run_worker_first` "is charged as a normal Worker invocation". The free limit is the
  same 100,000 a day.
- At that limit the site goes down. Cloudflare: with `run_worker_first`, requests over the
  free limit "will receive a 429 (Too Many Requests) response instead of falling back to
  static asset serving". Pages can serve the files anyway ("Fail open"). This is the reason
  `WEBSITE_ARCHITECTURE.md` gives for staying, and it holds for route A only.
- The host rules need rewriting. The middleware tells the project address from a preview by
  counting labels in a `*.pages.dev` name. On Workers the live address is
  `<worker>.<subdomain>.workers.dev` and a preview is
  `<preview-name>-<worker>.<subdomain>.workers.dev`: four labels each.
- `_headers` "are not applied to responses generated by your Worker code". Whether the
  kit's security headers would still reach a file the script passes through is not checked.

Route A costs a rewrite and ends up worse than Pages.

### Route B: drop the middleware

On Workers the platform can do both of the middleware's jobs:

- **Previews.** A Preview's `workers.dev` address "includes an `X-Robots-Tag: noindex`
  response header".
- **The project's own address.** `workers_dev = false` turns the live `workers.dev`
  address off, and "does not disable Version URLs, Preview URLs, or Deployment URLs". With
  that address off, the redirect has nothing left to redirect. Whether a live build still
  answers at one of those other addresses, and with which headers, is for the trial below.

If both hold on a real project, the site needs no script. Every request is then a file
request: no Functions requests, no daily limit, no Fail open setting, no `CANONICAL_URL`
step, no `middleware.spec.ts`.

One gap is open before launch. With the live `workers.dev` address off and no domain
attached yet, the live build has no address at all. The kit would have to pick: look at a
Preview until the domain is attached, or leave the address on until then. Cloudflare's
`workers.dev` page says nothing about noindex on that live address.

Route B is the only one worth doing, and it is the untested one. It rests on two sentences
in Cloudflare's docs.

## Pages and Workers side by side

What Cloudflare's docs say about each product. The Workers column was not tried on a
deployment; the trial list further down is for that. Of the Pages column, one thing was
seen on live sites: the middleware runs in front of plain files ("What is checked and what
is judgment"). The last column is a judgment, for a content site built with the kit.

| Topic | Pages | Workers | Better for a kit site |
|---|---|---|---|
| Cloudflare's direction | on all plans; the docs name no end date; stays supported, says Cloudflare's blog (April 2025) | called the "primary platform": "Start new projects with Workers"; is to get all new feature work, the same post announced | Workers |
| Plain files | free, no limit | free, no limit | the same |
| Code in front of every request | counts against 100,000 requests a day on the free plan; at the limit, Fail open keeps serving the files | counts the same; at the limit the request gets a 429 | Pages |
| A noindex header on previews | on every preview deployment | on a Preview's `workers.dev` address | the same |
| The project's own address | `<project>.pages.dev`; the docs offer a redirect and no way to turn it off | `<worker>.<subdomain>.workers.dev`; can be turned off | Workers |
| DNS for the domain | a subdomain can point here from another provider; an apex domain needs Cloudflare's nameservers | Cloudflare's nameservers, always | Pages |
| Setup | dashboard settings; finds `404.html` by itself | a config file in the repo; 404 handling must be set in it | Pages is simpler; Workers keeps the settings in the repo |
| A preview for each branch | yes, with controls per branch | yes; Workers Builds "does not yet have the same level of configurability" | Pages, slightly |
| `_headers`, `_redirects`, rollbacks | yes | yes | the same |
| Free limits | 20,000 files, 25 MiB a file, 100 projects an account | 20,000 files, 25 MiB a file, 100 Workers an account | the same |
| Logs for server code | real-time logs | real-time logs, Workers Logs, Logpush, source maps | Workers, once a site has server code |
| Cron Triggers, Queue consumers, Email Workers, rate limiting | no | yes | Workers, if a site ever needs one |
| Fit with the kit | the template, its tests and the docs are written for it | a move touches all of those, and each live site that follows needs its own switch | Pages |

For serving a static site the two are equal. Pages is ahead on what exists today: the kit
runs on it, Fail open keeps a site up at the free limit, and a subdomain's DNS can stay
elsewhere. Workers is ahead on where Cloudflare is going, and its own address can be turned
off, which route B relies on. Cloudflare's
[own table](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/#compatibility-matrix)
has more rows; the ones left out here do not bear on a content site.

| Preview at `main.<project>.pages.dev` | `<preview-name>-<worker>.<subdomain>.workers.dev`; the preview name defaults to the branch name | 15 files name `pages.dev`: nine in `new-website` (the middleware, its test, `ship.sh`, `PUBLISHING.md`, `AGENTS.md`, four more docs) and one each in six other skills |

| 20,000 files, 25 MiB a file (free) | the same | none |

And each live site that follows needs its own one-time move: a new Worker, the domain
attached to it, the Pages project deleted afterwards. A site can also stay on Pages for as
long as Pages is offered. How smooth that switch is for a live domain was not
looked at.

## What keeps working on Pages

Everything the kit uses is in Cloudflare's docs today: Git integration and direct upload,
[Functions middleware](https://developers.cloudflare.com/pages/functions/middleware/),
[Fail open / closed](https://developers.cloudflare.com/pages/functions/routing/),
[noindex on previews](https://developers.cloudflare.com/pages/configuration/preview-deployments/),
`_headers` and `_redirects`, custom domains. Cloudflare's sentence is about new projects,
its April 2025 blog post says Pages stays supported, and its migration guide sets no
deadline.

## What is checked and what is judgment

**Checked in Cloudflare's docs (2026-10-11):** every quoted sentence above, the address
shapes, the build variable names, the limits, the DNS rule. The blog post was read on
2026-10-12.

**Checked in the kit (`35e9b42`):** what the middleware does, which files read `CF_PAGES_*`,
which files name `pages.dev` or a `wrangler pages` command.

**Seen on live sites (2026-10-05):** on two sites built with the kit (an older middleware,
same place in `functions/`), a static file on the project address answered with the
middleware's redirect. On one of them, an image on a preview host carried the middleware's
header. So the middleware does run in front of plain files.

**Not checked:** anything on a real Workers project. Route B in particular.

**Judgment:** stay for now, because

1. nothing is broken on Pages, no end date is named, and Cloudflare says Pages stays
   supported;
2. a move touches template code, its tests, docs in seven skills and each live site that
   follows, for no gain a site owner would see today;
3. the target is still moving. Cloudflare's guide marked custom branch aliases on Workers
   "Coming soon" when read on 2026-10-05, and supported when read on 2026-10-11 (the guide
   was updated on 2026-10-10). Waiting costs little, and what the kit would move to keeps
   getting more complete.

**The best argument against staying:** route B removes the daily limit that every request
counts against on Pages today, and it deletes code and a setup step. Cloudflare calls
Workers its primary platform, and announced in April 2025 that all its new feature work
would go there. And every site scaffolded on Pages from now on is one more site to move
later, so waiting gets dearer with each new site.

## When to look again

- Cloudflare names an end date for Pages, or stops offering new Pages projects.
- A kit site hits the daily Functions limit in practice.
- A feature the kit wants exists on Workers only.
- Before a batch of new sites is scaffolded.

## If the kit does move: try it on one throwaway site first

Each line is something to look at, not an outcome to expect:

1. With `workers_dev = false` and Previews on, which addresses answer, and with which
   status?
2. Which response headers do a Preview URL and a Deployment URL carry? Is
   `X-Robots-Tag: noindex` on both, on pages and on files?
3. Do the headers from `public/_headers` arrive on the live domain and on a Preview?
4. Ask the deployed Preview directly; the site's tests run against a local Astro server and
   cannot. The starter ships no `public/_redirects`, so add one entry for the trial. Then,
   for a page the site has (the starter ships `/privacy`): what do `/privacy`,
   `/privacy.html`, `/privacy/`, the redirect entry and a path that does not exist answer,
   and with which status?
5. With `production` as the production branch and preview builds on, what does a push to
   `main` produce, and at which address? What does `npm run ship` then do?
6. What do `WORKERS_CI_BRANCH` and `WORKERS_CI_COMMIT_SHA` hold in a production build and in
   a preview build?
7. Before a domain is attached: with the live `workers.dev` address on, which headers does
   it carry?
8. After a day with traffic, which requests does the dashboard count against the daily
   limit?
